**2026-11-05 -- architect** -- START branch
`integrations-dev/itinerary-options-and-reviews`. Designing the multi-option planning
flow flagged in the previous entry. Decisions made up front so backend/integrations/UI
don't each invent their own:

- **New DB model `ItineraryOption`** (additive, no column dropped): `tripId`, `label`,
  `summary`, `pace`, `estimatedTotalCents` + `currency`, `draftJson` (the full option
  payload: days/activities + any attached review data), `status`
  (`PROPOSED | SELECTED | DISCARDED`), `optionIndex`. Options are *drafts* -- no
  `ItineraryDay`/`Activity`/`Booking` rows exist until one is chosen, so nothing can be
  booked against an option the user never picked.
- **New Trip status `CHOOSING`**, sitting between `PLANNING` and `BOOKING`. Follows the
  existing string-column + TS-union convention documented in `schema.prisma` (SQLite has
  no native enums); `packages/db/src/enums.ts` gets `CHOOSING` plus a new
  `ItineraryOptionStatus` union.
- **Three options generated by three separate ItineraryAgent calls**, one per variant
  framing, run in parallel -- *not* one call returning three itineraries. Reason: the
  existing single-itinerary tool schema is the one shape already proven against the real
  model (including the double-encoding repair path from the last live run); asking for 3x
  the output in one call triples the truncation/malformation surface at `max_tokens` and
  loses per-variant retry. `Promise.allSettled` so one bad variant degrades to 2 options
  instead of failing the trip.
- **Reviews are read-only comparison data, fully outside BookingAgent.** New
  `packages/integrations/src/reviews.ts` (Google Places) is called by the options-
  generation flow only. BookingAgent and the real booking tools are untouched.
- **Orchestrator split**: `planTrip()` is replaced by `generateItineraryOptions(tripId)`
  + `selectItineraryOption(tripId, optionId)`, with the persistence and booking-loop
  halves of the old `planTrip` extracted into shared internal helpers so selection reuses
  the exact same code path bookings already went through.

Handoff: `integrations-dev` (reviews adapter), `backend-dev` (schema + orchestrator +

gate), `devops` (migration + merge). Single branch, sequential roles -- the

**2026-11-05 -- ux-designer** -- Interaction spec for the options-comparison
view, for `frontend-dev` to implement on this branch. Written against design
commitment #2 (choosing is a real decision) and #4 (honesty about gaps).

**States on the trip dashboard**

| Trip status | What the user sees |
|---|---|
| `PLANNING` | "Drafting a few different versions of this trip…" + a note that it takes a minute and nothing is being booked yet. Three skeleton cards, so the shape of the coming decision is visible before it arrives. |
| `CHOOSING` | The comparison cards (below) + "Nothing is booked until you choose." Itinerary/booking sections stay hidden -- there is no itinerary yet. |
| `BOOKING`, itinerary not yet written | "Setting up <label>…" -- covers the ~1s between claiming the choice and the day rows existing, so the page never looks empty. |
| `BOOKING` onwards | Exactly today's dashboard: day-by-day itinerary, per-item booking pills, budget bar, notifications. Options are gone from the page -- the decision is made, re-litigating it is the revision feature's job, not this view's. |
| `NEEDS_ATTENTION` with no options and no itinerary | Option generation failed outright: say so plainly, say nothing was booked, tell them to try again with different dates/budget. |

**Each comparison card carries**, in this order (cost before prose -- it's the
thing people actually compare):
1. Label + pace badge.
2. Estimated total, explicitly marked **est.**, plus the delta against the
   cheapest option ("+$340 vs cheapest"). The cheapest card says "lowest
   estimate" instead. Copy must never imply this is a quote -- one shared
   footnote: "Estimates for comparison. Real prices come from the provider
   when we book."
3. Shape of the trip: N days, N activities, N things to book.
4. The summary paragraph.
5. **Named places with real rating badges** -- the hotel and any named tours:
   `4.6 ★ · 1,843 reviews` where we matched a real place, and the literal words
   **"No rating available"** where we didn't. Never a dash, never a zero, never
   a greyed-out star row that reads as "bad". One real review excerpt (verbatim,
   attributed) on the hotel, where we have one.
6. "Choose this plan" -- a real button per card, not a radio + submit.

**Why no rating** is stated once per card set, not per badge: "Google Places
isn't configured, so no ratings could be looked up" (NOT_CONFIGURED) vs "None
of these options named a specific place to look up" (NO_CANDIDATES) vs "Matched
real ratings for 2 of 4 named places" (OK). A user seeing an unrated hotel
needs to know whether that's the hotel's fault or ours.

**Choosing**: the clicked card's button becomes "Starting bookings…", every
other card's button disables immediately -- booking spends money, so a
double-click must look impossible, not just be rejected server-side. If the
server says it's already chosen (409), replace the cards with "A plan has
already been chosen for this trip -- booking is underway." rather than an
error, because that's what actually happened.

Handoff: `frontend-dev`.

**2026-11-05 -- qa-tester** -- Review gate on
`integrations-dev/itinerary-options-and-reviews`. Note on process: the
`/code-review` skill was invoked as the workflow requires, but its background
pass produced no findings after ~65 minutes and didn't answer a status ping, so
the gate was completed as the "equivalent review pass" the workflow allows
(`docs/team-workflow.md` item 3), structured against the qa-tester checklist.
Four real issues found and fixed on the branch:

1. **Stranded trip on a materialization failure** (`orchestrator.ts`). Any
   throw after the `CHOOSING -> BOOKING` claim left the trip in `BOOKING` with
   no itinerary, no options on screen, and no way back. Now releases the claim.
2. **Non-atomic option marking** (`orchestrator.ts`) -- the worse half of the
   same area. The `SELECTED`/`DISCARDED` writes sat outside
   `materializeItinerary`'s transaction but inside the revert's `try`. Had they
   failed after the days/bookings landed, the revert would have left real
   itinerary rows behind, and the unique `(tripId, dayIndex)` index would then
   make *every* retry fail permanently. Folded into the one transaction.
3. **Rate-limit hint ignored** (`reviews.ts`) -- mapped every 429/quota 403 to a
   flat 1s `retryAfterMs`, where `tours.ts` already reads `Retry-After`. Now
   consistent.
4. **Rating badge unlabelled** (`ItineraryOptions.tsx`) -- announced as a bare
   "4.6 · 1,843 reviews" with no indication it was a rating or whose. Added an
   `aria-label`.

Money/idempotency/ordering checks: estimates are integer cents end to end
(live-verified 205000 == $2,050, model got minor units right); option currency
comes from the trip, not the model, so an option can't disagree with the budget's
currency; the budget-before-booking ordering in `processBooking` is untouched;
`BookingAgent` and the booking tools are untouched by this branch entirely.

**What the revision-prompt branch needs to know before it starts:**
- **`planTrip()` no longer exists.** It's split into
  `generateItineraryOptions(tripId)` and
  `selectItineraryOption(tripId, optionId)`. The reusable internals are
  `materializeItinerary(tripId, optionId, brief, days)` (one transaction:
  days + activities + bookings + option status) and
  `runBookingPipeline(items)` -> `finalizeTripStatus(tripId)`. Re-plan a trip
  by composing those, don't re-implement persistence.
- **New Trip status `CHOOSING`** between `PLANNING` and `BOOKING`
  (`packages/db/src/enums.ts`), plus `ItineraryOptionStatus`
  (`PROPOSED | SELECTED | DISCARDED`). Any revision flow that re-opens planning
  on an already-booked trip has to decide what it does with existing
  `Booking` rows *before* it sends the trip back to `CHOOSING` -- this branch
  deliberately doesn't touch that.
- **`persistOptions()` calls `deleteMany` on the trip's options** before writing
  a new set (the `(tripId, optionIndex)` unique index requires it). It is only
  ever called pre-choice today. If the revision flow calls
  `generateItineraryOptions` on a trip that already has a SELECTED option and a
  materialized itinerary, that delete will drop the chosen option while its
  itinerary rows survive -- guard it there.
- **`OrchestratorError`** (`code: OPTION_NOT_FOUND | OPTION_ALREADY_CHOSEN`) is
  the pattern for flow failures that need a specific HTTP status; extend it
  rather than throwing bare `Error`s.
- **`reviews.ts` is read-only and must stay out of BookingAgent.** It's also the
  one adapter with no sandbox mode (Google publishes none) -- fine while it
  can't spend money, not fine if that ever changes.
- The trip dashboard is now `max-w-5xl` and renders options only while
  `status === "CHOOSING"`; the persistent "revise this trip" surface should sit
  outside that branch so it's visible in every state, per `ux-designer.md`.

**2026-11-05 -- qa-tester** -- Addendum: the `/code-review` background pass
*did* eventually return, shortly after the merge above. It independently
confirmed both bugs I'd already found and fixed (the stranded CHOOSING claim
and the non-atomic option marking) and raised 10 more. All fixed on
`qa-tester/options-review-fixes` and merged; `npm run typecheck`, `npm test`
(24 tests now), and `npm run build -w apps/web` pass, and the whole flow was
re-run live on a fresh Rome trip afterwards.

Worth recording because it's the pattern, not the individual bugs: **every
HIGH/MEDIUM finding was a state the happy path never visits.** The options
fetch failing (error written to a state that only renders inside the component
that isn't mounted yet). A clarification prompt answered after booking (nothing
in this app ever marks a notification read, so that prompt never goes away on
its own). The ratings provider configured but rate-limited, which my own code
reported as "matched 0 of 4" -- i.e. the code whose header insists on
distinguishing "we never looked" from "we looked and found nothing" was itself
blurring them. None of those show up in a live run with no keys and a working
model, which is exactly why the gate isn't optional.

One finding I deliberately did not "fix": `POST /api/trips/[id]/choose` has no
ownership check. It's the first endpoint in the repo that commits spend, so the
blast radius of the known pre-auth state is now larger -- but inventing
half-auth on this branch would be worse than the documented gap. Recorded in
`docs/architecture.md`'s known gaps; it belongs with the real auth work.

Also of note for `backend-dev`: I had to make `pace` and `estimatedTotalCents`
lenient (`.catch()` / `z.coerce`) because strict parsing threw away an entire
valid multi-day itinerary when the model wrote `"moderate"` or `"185000"` for a
field we only ever render on a badge. Strictness should match what a field is
load-bearing for -- `searchHint` and `kind` stay strict because they decide what
gets booked. The tool-input repair list stays `["days"]` on purpose: pushing
`label` through `JSON.parse` would turn a numeric-looking label like "2024" into
a number and fail validation that would otherwise have passed.
